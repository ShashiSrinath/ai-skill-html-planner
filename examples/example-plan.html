FEATURE PLAN

Session persistence

Today a session is a single cookie that dies with the browser, and any server restart forces every user to sign in again. This plan introduces durable sessions backed by a rotating refresh token and a per-device registry, so users stay signed in across restarts and can revoke a single device without logging out everywhere. The goal is to cut re-login friction without weakening the security posture of the auth service.

In review 2026-08-11 Author: S. Okafor Owner: Identity squad

Context and problem

The auth service issues a single HttpOnly session cookie that is cleared when the browser closes. Because the cookie holds no server-side record, there is no way to distinguish one device from another, and revoking a session means invalidating every session at once. Three structural problems follow:

  • Sessions are cookie-only and die with the browser, so closing a tab is a logout.
  • There is no refresh-token rotation, so a long-lived token cannot be replaced on use.
  • Revocation is a global logout, not a per-device action, which punishes one lost laptop.

A refresh-token pair with a device registry addresses all three: the access token stays short-lived, the refresh token rotates on every use, and each device can be revoked independently.

Goals

Durable sessions

Keep a user signed in across browser restarts and server restarts for up to 30 days, matching the current cookie lifetime but without the browser-close logout.

Per-device revocation

Let a user list active devices and revoke any single one from the security settings page, without affecting the others.

Refresh rotation

Replace the refresh token on every use so a stolen token is only valid for a single exchange and reuse is detected and flagged.

Zero login-rate regressions

Keep the forced re-login rate at or below today's level while the new token flow is rolled out, measured against the same cohort definition.

Implementation

  1. Issue a token pair. On sign-in, mint a short-lived access token and a long-lived refresh token, and return the refresh token in an HttpOnly cookie.
  2. Rotate on refresh. On every refresh call, validate the presented token, issue a new pair, and mark the old refresh token as used so it cannot be replayed.
  3. Store hashed refresh tokens. Persist only a hash of each refresh token server-side, so a database leak does not expose usable credentials.
  4. Add a device registry. Record a device id, user agent, and last-seen time per session so the security page can render a per-device list.
  5. Wire revocation endpoints. Add a revoke-by-device endpoint that deletes the matching session row and clears the cookie, and keep the existing global logout as a fallback.

Decision

Store the refresh token in an HttpOnly cookie with rotation, and keep the access token short-lived in memory — not in localStorage. localStorage is readable by any script on the origin and would expose the token to XSS; an HttpOnly cookie keeps the refresh token out of JavaScript entirely, and rotation limits the blast radius of any single leak.

Open questions

What idle-timeout policy should apply to durable sessions? A fixed 30-day lifetime is simple, but an inactivity-based timeout would better match how the product team expects shared devices to behave.

Should the same device be allowed to hold multiple concurrent sessions, for example one per browser profile? The device registry currently assumes one session per device id, which may be too strict for power users.

Code

The rotation helper is the single source of truth for the token lifecycle. It validates the presented refresh token, marks it used, and returns a fresh pair so a replayed token is rejected on the next exchange. 

export async function rotate(refresh: string, store: SessionStore) {
  const row = await store.findByHash(hash(refresh));
  if (!row || row.used) throw new Unauthorized("stale or replayed token");
  await store.markUsed(row.id);
  const next = await issuePair(row.userId, row.deviceId);
  await store.save(hash(next.refresh), row.userId, row.deviceId);
  return next;
}

The device registry keeps the per-device list that powers the security page. Each entry records the device id, a friendly label, and the last time it was seen, so a user can revoke a single device without touching the others. 

export class DeviceRegistry {
  constructor(private store: SessionStore) {}

  async list(userId: string): Promise<Device[]> {
    return this.store.listDevices(userId);
  }

  async revoke(userId: string, deviceId: string): Promise<void> {
    await this.store.deleteByDevice(userId, deviceId);
  }
}
