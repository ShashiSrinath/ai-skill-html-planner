AI-SKILL-HTML-PLANNER

The Design System for AI-Authored Documents

This is the living style guide for ai-skill-html-planner. Agents write minimal, semantic HTML and mark it with a small set of pl-* classes; this versioned stylesheet renders those documents as polished, professional pages. The zero-class baseline means even a document with no classes at all still looks deliberate.

v0.1.0 Style guide 2026-08-11 MIT licensed

Zero-class baseline

Semantic HTML with no classes renders correctly. This is the anti-slop guarantee: an agent can emit plain markup and the document still reads well, so a well-chosen class only adds structure rather than repairing broken layout. The block below uses only bare elements — no classes anywhere.

.callout

Use for a highlighted note, warning, decision, or open question. The kind sets the accent, and the title appears in a small header row.

The CDN tags are immutable. Once a version is published, its pinned tag never changes, so a document that references v0.1.0 will render identically forever.

The dist/ directory is build output. Never hand-edit it; regenerate it from src/ with the build script so the compiled allowlist stays in sync with the source.

Use no webfonts. A system font stack keeps every document offline-clean and free of layout shift, at the cost of some typographic consistency across operating systems.

Will dark mode stay automatic, driven by prefers-color-scheme , or will it grow a manual toggle for authors who want a fixed look in embedded contexts? 

<div class="callout" data-kind="warn" data-title="Warning">
  <p>Body text of the callout.</p>
</div>

.steps

Use for a numbered sequence of actions that must happen in order. Each item leads with a bolded step name.

  1. Scaffold from a template. Copy the plan, adr, or retro template so the skeleton and imports are already correct.
  2. Write the content. Fill in prose and markup using only the allowlisted classes.
  3. Format the file. Run the formatter so whitespace and attribute wrapping are consistent.
  4. Validate the file. Run planner validate and fix every error and warning.
  5. Open the document. Serve it and confirm the TOC and any runtime behavior are present. 
<ol class="steps">
  <li><strong>Step name.</strong> Step body text.</li>
  <li><strong>Next step.</strong> Step body text.</li>
</ol>

Typography

The type stack is deliberately system-first: a clean sans-serif for body text and a monospace stack for code. No webfonts are loaded, so documents stay fast and render the same offline. Sizes follow a modest scale tuned for long-form reading.

Element Size Weight
h1 2.2rem 700
h2 1.5rem 650
h3 1.15rem 600

Inline code is set with code , for identifiers such as planner validate and paths like site/index.html . Keyboard input is marked with kbd , as in press Enter to continue or hold Shift to extend a selection.

A regular link such as the project home keeps a visible underline and a clear focus ring.

Text selection is tinted to match the accent, and every focusable element gets a visible focus-visible ring so keyboard users can trace where they are.

Rules of the system

Three rules keep generated documents consistent. No emoji, no inline styles, and no invented classes. The validator enforces all three, so a document either passes or it is not shipped.

Run planner validate before you open a document. It is the quality mechanism — it catches a stray emoji, an inline style, or an off-allowlist class in one pass.

The allowlist is derived from the compiled CSS. New classes must land in src/ and be built into dist/ before they can be used; a class added only in a document is a warning.

  • Use only allowlisted classes.
  • Never hand-write section numbers.
  • Let the TOC build itself.
  • Keep prose concrete and specific.
